# Publication contract v1.0 (S2S)

The Tek Juice Data Engine publishes approved content to a customer backend by
calling the backend's **publication endpoint**, served by
`tekjuice_connector.publication.PublicationReceiver`. This document is the
exact wire contract. The receiver implements it; customers only supply a
`ContentStore` and mount an adapter.

## Transport and authentication

| Item | Value |
|---|---|
| Method | `POST` to the registered endpoint URL (HTTPS, default port, public DNS name) |
| `Authorization` | `Bearer <receiver secret>` — compared in constant time |
| `X-TekJuice-Contract-Version` | `1.0` |
| `Content-Type` | `application/json` |
| `Idempotency-Key` | publish requests only; equals body `idempotency_key` |
| Body limit | 2 MiB by default (`413` above it) |
| Data Engine timeout | 30 s per publish, 15 s per verification |

Two credentials are involved and are never interchangeable:

- **Connector key** — issued by the Data Engine, sent by the connector in
  `X-Tek-Juice-Connector-Key` to authenticate the handshake. Stored hashed by
  the Data Engine.
- **Receiver secret** — generated by the customer (`secrets.token_urlsafe(48)`),
  sent once per handshake inside the authenticated request, stored encrypted
  by the Data Engine, and presented by the Data Engine as the bearer token on
  every publication. Never returned by any Data Engine API.

## Registration (connector → Data Engine)

`POST /api/v1/connector/handshake` with header `X-Tek-Juice-Connector-Key`:

```json
{
  "website_id": "<website id>",
  "publication": {
    "endpoint_url": "https://api.example.com/tekjuice/publish",
    "auth_scheme": "bearer",
    "receiver_secret": "<receiver secret>",
    "contract_versions": ["1.0"],
    "capabilities": ["publish.create", "publish.update", "publish.verify"],
    "framework": "fastapi"
  }
}
```

The response adds, to the 0.1.0 fields, `publication_status`
(`not_configured` | `pending_verification` | `verified` | `failed`),
`publication_ready` and `next_action`. `ready` is `true` only when onboarding
is `READY` **and** the publication connection has been verified.

Registration alone never enables publishing. The Data Engine then verifies
the connection (below) and activates it only if verification succeeds.
Re-sending an identical registration is a no-op; a changed endpoint, secret
or capability set deactivates the connection until it is re-verified.

## Capabilities

| Capability | Meaning | Advertised when |
|---|---|---|
| `publish.create` | accepts `action: create` | always (store implements `create`) |
| `publish.update` | accepts `action: update` | store implements `update` |
| `publish.verify` | accepts `action: verify` dry runs | always |

The Data Engine requires `publish.create` and `publish.verify`, and contract
version `1.0`, before it will attempt verification.

## Publish request

```json
{
  "contract_version": "1.0",
  "execution_id": "<Data Engine content execution id>",
  "website_id": "<website id>",
  "action": "create",
  "idempotency_key": "tekjuice:<website>:<execution>:<action>:<sha256>",
  "content": {
    "title": "Moving Cost Guide",
    "body": "<h1>…</h1>",
    "slug": "moving-cost-guide",
    "excerpt": "…",
    "meta_description": "…",
    "meta_keywords": ["moving costs"]
  },
  "metadata": {
    "content_strategy_id": "…",
    "opportunity_id": null,
    "content_hash": "<sha256 hex>"
  }
}
```

Validation (all failures are `422`, never retried):

- unknown fields are rejected at every level;
- `slug`: `^[a-z0-9]+(-[a-z0-9]+)*$`, at most 120 characters — never a path,
  URL or domain;
- `title`, `body`, `execution_id`, `idempotency_key` non-empty strings;
- `content_hash`, when present, must equal SHA-256 of
  `title \n body \n slug \n excerpt \n meta_description \n keywords-joined-by-comma`
  (absent optional values as empty strings).

### Content identity and semantics

Content is identified by **slug**; the store records, with each piece of
content, the `execution_id` and `idempotency_key` that last wrote it.

| Action | Condition | Result |
|---|---|---|
| any | `idempotency_key` already applied | `200`, `replayed: true`, nothing written |
| `create` | slug free | create, `action_performed: created` |
| `create` | slug held by the same `execution_id` (regenerated content) | overwrite, `action_performed: updated` |
| `create` | slug held by different content | `409 duplicate_slug` |
| `update` | store lacks `publish.update` | `422 unsupported_operation` |
| `update` | slug not found | `404 target_not_found` — updates never create |
| `update` | slug found | overwrite, `action_performed: updated` |

### Success response (`200`)

```json
{
  "status": "published",
  "contract_version": "1.0",
  "action": "create",
  "action_performed": "created",
  "replayed": false,
  "persisted": true,
  "website_id": "<website id>",
  "execution_id": "<echoed>",
  "idempotency_key": "<echoed>",
  "resource_id": "<customer resource id>",
  "slug": "moving-cost-guide",
  "content_hash": "<sha256 of stored content>",
  "published_url": "https://www.example.com/moving-cost-guide"
}
```

`execution_id`, `idempotency_key` and `content_hash` let the Data Engine tie
the result to the exact execution job and content it sent.

## Verify request (readiness check, never persists)

```json
{
  "contract_version": "1.0",
  "action": "verify",
  "website_id": "<website id>",
  "challenge": "<one-time random value>",
  "dry_run": true,
  "publication": { "<a complete publish request>": "…" }
}
```

The receiver authenticates, validates the embedded publication exactly as a
real publish (including duplicate-slug and the store's optional `validate`
hook), and returns:

```json
{
  "status": "verified",
  "contract_version": "1.0",
  "challenge": "<echoed>",
  "website_id": "<website id>",
  "persisted": false,
  "capabilities": ["publish.create", "publish.update", "publish.verify"],
  "contract_versions": ["1.0"],
  "would_publish_url": "https://www.example.com/tekjuice-verification-…"
}
```

The Data Engine marks the connection verified only if: HTTP 200, `status`
is `verified`, the challenge and `website_id` match, `persisted` is `false`,
the required capabilities are confirmed, and `would_publish_url` is HTTPS on
the website's domain or a subdomain.

## Errors

```json
{"status": "error", "error": {"code": "duplicate_slug", "message": "…", "retryable": false}}
```

| HTTP | `code` | Retried by the Data Engine |
|---|---|---|
| 400 | `malformed_request` | no |
| 401 | `unauthorized` | no |
| 403 | `website_mismatch` | no |
| 404 | `target_not_found` | no |
| 409 | `duplicate_slug` | no |
| 413 | `request_too_large` | no |
| 422 | `contract_violation`, `unsupported_contract_version`, `unsupported_operation` | no |
| 500 | `publication_error` (unexpected store failure, details withheld) | yes, bounded |
| 503 | `storage_unavailable` (store raised `ContentStoreError`) | yes, bounded |

The Data Engine retries 5xx, 408, 425, 429 and network failures up to 3
attempts, then marks the job failed; 4xx failures are terminal until an
explicit recovery.

## Migrating a legacy M2M receiver

S2S is the Data Engine's only publication transport; its M2M transport is
retired and is never used as a fallback. Hand-written receivers built for
M2M (for example the UMET backend's `/api/integrations/tekjuice/publish`)
accept the same publish body but cannot answer `action: verify`, so they can
never become publication-ready.

To migrate, implement a `ContentStore` over the receiver's existing content
model and ledger, mount `PublicationReceiver` on a new route next to the old
one, and run the connector handshake with that route as the endpoint. Keep
the old route until the Data Engine reports `publication_ready`, then remove
it. Content and ledger history written over M2M stays in place and remains
updatable over S2S, because the store reads the same tables.
